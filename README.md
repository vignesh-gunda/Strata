# Strata

> Dig through a black box layer by layer, rebuild it in a new language, and prove the rebuild behaves the same.

Strata is an agent that reverse-engineers a program it has never seen. The program is **Pressure**, a small card game for 2 to 4 players. The agent gets only a `dig-site/` folder of incomplete evidence: a runnable binary, recorded game traces, a partly lost source file and an old manual that is partly wrong. It plays test games, writes down what it learns in an evidence ledger, rebuilds the game in JavaScript or Go, and proves the rebuild matches the original game by game.

Everything runs on your machine. There is no hosted service.

## What it does

1. **Survey.** Reads the manual and the partial code as *claims* (never as facts) and ranks what is unknown: lost functions and missing values first.
2. **Audit.** Checks those claims against the recorded games. Where the manual or code disagrees with the traces, it keeps a *finding* with the trace ID. Nothing is deleted.
3. **Probe and hypothesize.** Plays targeted games against the binary. Meta Muse Spark proposes rules as small programs; a scorer written in plain code runs them on every recorded step and decides which are Confirmed or Refuted.
4. **Rebuild.** Muse writes the engine from Confirmed rules only. Behavior no rule covers is left as an explicit "unknown", never guessed.
5. **Verify.** Replays every recorded game and fuzzes thousands of new ones through both programs. Any difference is shrunk to the shortest failing game and sent back for repair.
6. **Report.** Lists where the evidence was wrong, what is Confirmed, Inferred or Open, whether the rebuild is equivalent, and (after the run) which planted changes were found.

### Rules the code enforces

- Only traces can move a claim to Confirmed or Refuted. A claim with no trace ID cannot.
- Only the scorer may write Confirmed or Refuted. No model call holds that authority.
- The binary is a process to run, never a file to read.
- Nothing from `services/` (the original program) enters a prompt or a tool result. A prompt firewall blocks it.
- Model-written code runs in a separate process with a time limit and no API keys.
- Keys come from `.env` and are never logged, printed or sent to a prompt.

## Layout

| Path | What it is |
|---|---|
| `dig-site/` | The only evidence the agent gets. Generated by `services/pressure/tools/build_dig_site.py` (see `dig-site/README.md`) |
| `services/pressure/` | The original game and its answer keys. **The agent never reads this.** See its README |
| `agent/` | The agent, one folder per sub-agent, each with `main/` and `tests/`. Task plan in `agent/tasks.md` |
| `rebuild/` | The rebuilt code: `rebuild/<run_id>/<language>/` (engine, contract server, notes and rule files). Generated, ignored by git |
| `ui/` | The browser app: a live game table plus a "Behind the scenes" view of the ledger and the agent's action feed |
| `scripts/` | `check_keys.py` (API key smoke test), `check_repo.py` (pre-publish checks), `rehearse.py` (offline demo rehearsal) |
| `pitch/` | One-page pitch |

Agent components (`agent/<name>/main`): `llm` (Muse and SubQ clients, budget guard, prompt firewall), `sandbox` (jailed file access, the binary as a process, safe execution of model code), `ledger`, `surveyor`, `auditor`, `prober`, `scorer`, `hypothesizer`, `rebuilder` (JavaScript and Go), `verifier`, `coordinator` (chat and background runs), `concierge` (plain-language questions), `livefeed` (one line per agent action), `report`, `controls` (offline checks on a saved run).

## Setup

Needs Python 3.12 (the dig-site binary requires it) and Node 20 or newer. Go 1.21 or newer is optional and only needed to rebuild in Go.

```bash
# 1. API keys, in a .env file at the repo root (ignored by git)
printf 'META_API_KEY=...\nSUBQ_API_KEY=...\n' > .env
python3 scripts/check_keys.py            # one tiny call to each service; prints PASS or FAIL

# 2. Build the dig-site (binary, traces, partial code, manual). Seed and mutations are your choice.
cd services/pressure
python3 -m venv .venv && .venv/bin/pip install -r requirements-dev.txt
.venv/bin/python -m tools.build_dig_site --seed 42 --mutations 2 --games 40 --run-id r-01
cd ../..

# 3. The agent
cd agent
python3.12 -m venv .venv && .venv/bin/pip install -r requirements-dev.txt
```

## Run it

All agent commands run from `agent/` and write to `agent/runs/<run_id>/`; the rebuilt code goes to `rebuild/<run_id>/<language>/` at the top of the project. Both are ignored by git.

```bash
cd agent

# Talk to it. "rebuild it in Go", "what did you find wrong in the manual?", "status", "open questions"...
.venv/bin/python -m coordinator.main.chat --run-id r-01

# Or run the stages yourself, in order
.venv/bin/python -m surveyor.main.survey          --run-id r-01      # no game is played
.venv/bin/python -m auditor.main.audit            --run-id r-01
.venv/bin/python -m hypothesizer.main.hypothesize --run-id r-01      # probes, rules, scoring
.venv/bin/python -m rebuilder.main.cli            --run-id r-01 [--language go]
.venv/bin/python -m report.main.cli               --run-id r-01      # writes report.md

# Watch it
.venv/bin/python -m livefeed.main.stream --run-id r-01 --follow      # tail the live feed
.venv/bin/python -m livefeed.main.stream --run-id r-01 --replay 20   # replay a saved run at 20x
cd .. && agent/.venv/bin/python -m ui.server --run-dir agent/runs/r-01   # then open http://localhost:8765
```

In the chat, "start" or "rebuild it in Go" runs the whole pipeline in the background and posts one line per step as it happens. If a stage fails it stops, keeps its progress and resumes from there on the next "start".

## Test it

```bash
cd agent && .venv/bin/python -m pytest                  # the agent (uses recorded fixtures, no live model calls)
agent/.venv/bin/python -m pytest                        # from the repo root: the UI
cd services/pressure && .venv/bin/python -m pytest      # the original game
python3 scripts/check_repo.py                           # before publishing: ignored files, secrets, isolation
agent/.venv/bin/python scripts/rehearse.py              # offline demo rehearsal (no keys, no network)
```

Tests that need the Go toolchain or a built dig-site skip themselves when it is missing.

## Demo and fallback

`scripts/rehearse.py` builds a fresh run from the dig-site with the code-only stages, then checks every way the demo can be shown: the terminal feed replayed, the UI served from the run folder, the chat answering from the ledger, and the report. If live model calls are slow or down on the day, `--keep` saves that run to `agent/runs/rehearsal/` and the same demo plays from disk:

```bash
agent/.venv/bin/python scripts/rehearse.py --keep
agent/.venv/bin/python -m ui.server --run-dir agent/runs/rehearsal
```

The UI's feed can also replay any saved run: `/api/feed?replay=20`.

## Controls

`python -m controls.main.cli --run-id r-01` re-scores a saved run's rules without calling a model:

- a learning curve over probe count, with the zero-probe baseline,
- a probe-order comparison standing in for "traces only vs traces plus artifacts",
- an opaque-token check that renames every card and confirms the scorer reaches the same ledger.

## Honest limits

- The controls replay a saved run. They show how the scoring behaves; they cannot show whether the agent would have found the same rules from opaque names or without the manual, because that needs fresh Muse runs. On the one run measured, both probe orders confirmed the same rules, and the artifact-informed order did not uniformly need fewer probes (it reached every new kind of situation, the other order reached half and nine tenths of them sooner but never all).
- The Go rebuild is tested with a toy engine and a real Go toolchain. A full Go rebuild of Pressure from live Muse output has not been run.
- Keyword matching decides whether a planted change counts as "found" in the report. Check each row by hand.
- Confirmed means: no mismatch on any recorded step including held-out games, and separated from rival rules by an experiment. It does not mean every possible game was tried; the Verifier's fuzzing is the check on that.
- Some behaviors stay Open or Inferred. The report says so rather than filling the gap.
